## 1. 背景与目标

### 1.1 问题定义

AI 助手天然无状态：每次会话从零开始，跨会话遗忘。直接解法有三种，各有致命缺陷：

| 方案 | 缺陷 |
|---|---|
| 全量历史塞入上下文 | Token 成本爆炸，超出模型上下文窗口 |
| 只靠用户手动维护记忆文件 | 维护成本高，用户会放弃 |
| 只靠向量检索历史对话 | 每次都要检索，延迟高，且"该记住的结论"反复被重新推导 |

### 1.2 设计目标

WorkBuddy 采用**分层记忆架构**，目标三角：

1. **成本可控**：常用信息常驻（画像+记忆文件，千级 token），长尾信息按需检索
2. **主权分级**：云端自动学习（零维护）与本地显式记忆（用户可控）并存
3. **新鲜度管理**：稳定信息长期保留，时效信息自动衰减

---

## 2. 术语定义

| 术语 | 定义 |
|---|---|
| 云端画像 | 服务端基于全部历史会话自动蒸馏的用户画像，会话开始时注入，本地只读 |
| 跨会话检索 | 服务端对全部历史对话建立索引，按需检索的工具能力 |
| 用户级本地记忆 | `~/.workbuddy/MEMORY.md`，跨项目生效，Agent 显式写入 |
| 工作区记忆 | `{workspace}/.workbuddy/memory/` 下的每日日志与项目长期记忆 |
| 蒸馏 | 将低层原始记录（日志/会话）压缩为高层结论（长期记忆/画像）的过程 |
| 稳定层 / 时效层 | 画像内部按信息生命周期划分的两类数据 |

## 3. 现状分析：三层记忆体系

### 3.1 架构总览

```
┌─────────────────────────────────────────────────┐
│ Layer 1 · 云端（跟随账号，跨设备）                  │
│   1a 云端画像（自动蒸馏 · 会话开始注入 · 只读）      │
│   1b 跨会话检索（全量对话索引 · 按需调用）           │
├─────────────────────────────────────────────────┤
│ Layer 2 · 用户级本地（跨项目，跟随机器）             │
│   ~/.workbuddy/MEMORY.md（Agent 显式写入）         │
├─────────────────────────────────────────────────┤
│ Layer 3 · 工作区本地（仅当前项目）                  │
│   3a 每日日志 YYYY-MM-DD.md（只追加）              │
│   3b 项目长期记忆 MEMORY.md（蒸馏写入）             │
└─────────────────────────────────────────────────┘
```

> 注：「三层」指三个存储层级（云端 / 用户级本地 / 工作区本地），下含五个组件（1a 画像、1b 检索、2 用户级、3a 日志、3b 项目长期）。

### 3.2 各层职责矩阵

| 维度 | L1a 云端画像 | L1b 跨会话检索 | L2 用户级本地 | L3a 每日日志 | L3b 项目长期 |
|---|---|---|---|---|---|
| **存储位置** | 服务端 | 服务端索引 | 本地文件 | 本地文件 | 本地文件 |
| **写入方** | 服务端自动 | 系统自动（全量对话） | Agent 显式 | Agent 追加 | Agent 蒸馏 |
| **读取时机** | 会话开始自动注入 | 按需（工具调用） | 会话开始注入 | 按需读取 | 按需/会话开始 |
| **容量约束** | 约 1–2K token | 无限（全量索引） | 4000 字/会话 | 无硬限 | 3000 字/会话 |
| **生命周期** | 长期 + 内部衰减 | 永久 | 长期 | 30 天后蒸馏 | 长期 |
| **用户可控性** | 低（只读） | 低 | 高 | 高 | 高 |
| **作用域** | 账号级 | 账号级 | 用户机器级 | 单项目 | 单项目 |

### 3.3 协同机制（实测行为）

**注入机制（会话开始）**：云端画像以只读形式注入上下文，并明确警告"本地写入会在下次会话被服务端覆盖"——说明画像有服务端权威源，本地无写入口。

**强制提醒（每轮注入）**：运行时在每轮用户消息中注入记忆写入提醒，内容包括：今日日志是否存在（不存在则先创建）、写入路由规则、跳过条件。这保证写入策略是**产品级强制**而非依赖模型自觉。

**写入路由决策树**（Agent 每轮执行的判定逻辑）：

1. 内容是跨项目的个人习惯/偏好？→ 写 L2 用户级
2. 内容是本项目的当日实质工作？→ 追加 L3a 每日日志
3. 内容是本项目的长期约定/事实？→ 写 L3b 项目记忆
4. 用户要回忆历史某次讨论？→ 调用 L1b 检索，**不落本地文件**
5. 打招呼/简单查询/短问答？→ 不写任何层

**跳过条件**：问候、简单查询、短问答不触发写入；临时信息（搜索结果、临时路径、工具报错）禁止入长期记忆。

**维护机制**：每日日志超过 30 天 → 按主题蒸馏进项目长期记忆 → 删除原日志。除用户明确要求外不存密钥。

**检索边界（关键设计）**：跨会话检索工具**零访问当前会话上下文**，查询必须自包含（描述目标 + 时间范围 + 背景）。推测设计意图：避免查询依赖当前上下文，使检索可在服务端独立执行与排序（约束为实测，意图为推断）。

### 3.4 设计亮点分析

1. **读写分离的信任模型**：云端层只读（防本地篡改导致画像污染），本地层用户全权可控（隐私兜底）——学习与主权分治。
2. **"结论常驻 + 原始按需"的两级检索经济学**：值得记的结论进小文件常驻；不值得常驻的细节留在服务端索引，偶发回访才检索。
3. **提醒常驻但规则下沉**：每轮只注入轻量提醒（路由要点），完整规则在系统层——控制每轮 token 开销。
4. **容量硬限反向约束写入质量**：4000/3000 字上限迫使 Agent 做"值不值得记"的筛选，天然防膨胀。

## 4. 用户画像功能（服务端）需求设计

### 4.1 需求背景

画像解决的是本地记忆解决不了的两个缺口：

- **隐式学习**：用户没让记、但系统观察到的长期模式（工作背景、沟通偏好），本地 MEMORY.md 只能记显式确认的信息
- **覆盖面**：本地记忆受会话写入量限制，画像的数据源是全部历史会话，跨项目、跨设备跟随账号

### 4.2 用户故事

| 编号 | 用户故事 |
|---|---|
| US-01 | 作为用户，我希望新会话开始时 AI 就了解我的工作背景和偏好，不用每次自我介绍 |
| US-02 | 作为用户，我希望我没明说的工作习惯（如偏好表格输出）能被自动识别并应用 |
| US-03 | 作为用户，我希望过时的信息（上个月在忙的项目）自动从画像中淡出 |
| US-04 | 作为用户，我希望问"我们之前怎么定的"时，AI 能检索到历史讨论原文 |
| US-05 | 作为用户，我希望我的记忆数据在我可控的范围内（本地可见、可删） |

### 4.3 画像数据模型（逆向推断）

实测注入的画像结构包含四个维度，本质是**稳定层 + 时效层**的双层模型：

| 层 | 维度 | 内容示例 | 更新频率 | 过期策略 |
|---|---|---|---|---|
| 稳定层 | 工作背景 | 公司、角色、主责项目、技术栈 | 低频修订 | 不过期，冲突时覆盖 |
| 稳定层 | 个人背景 | 沟通语言、输出风格偏好、协作习惯 | 低频修订 | 不过期 |
| 时效层 | 当前关注 | 本周并行任务、进行中的决策 | 高频追加 | 滚动窗口衰减 |
| 时效层 | 近期动态 | 具体进展条目（带时间） | 高频追加 | TTL 衰减（推断约 30 天量级） |

### 4.4 功能需求（FR）

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-01 | 隐式画像生成 | P0 | 服务端基于全部历史会话自动蒸馏画像，无需用户操作 |
| FR-02 | 双层结构存储 | P0 | 画像按稳定层/时效层组织，各层不同更新与过期策略 |
| FR-03 | 会话开始自动注入 | P0 | 画像随会话初始化注入上下文，对 Agent 呈只读 |
| FR-04 | 本地写保护 | P0 | 本地对画像缓存文件的修改在下次会话被服务端覆盖 |
| FR-05 | 跨会话全文检索 | P0 | 对全部历史对话建立索引，支持语义/关键词排序 |
| FR-06 | 检索查询自包含 | P1 | 检索工具不访问当前会话上下文，查询须自带完整描述 |
| FR-07 | 每轮写入提醒注入 | P0 | 运行时每轮注入记忆路由提醒，保证写入策略强制执行 |
| FR-08 | 分层写入路由 | P0 | Agent 按作用域路由写入（用户级/项目日志/项目长期） |
| FR-09 | 日志周期蒸馏 | P1 | 30 天以上每日日志按主题蒸馏进项目长期记忆后删除 |
| FR-10 | 敏感信息保护 | P0 | 非用户明确要求不入密钥类信息；画像脱敏 |

### 4.5 画像更新管线（核心机制）

```
触发（会话结束 / 显式指令 / 周期任务）
  → 提取（LLM 蒸馏候选事实，置信度分级）
  → 分类（稳定层 or 时效层）
  → 合并（稳定层：修订覆盖 / 时效层：追加 + TTL 衰减）
  → 画像文件（容量硬限，超限先压时效层）
  → 下一会话注入（闭环）
```

**信号强度分级（提取环节的置信度门槛）**：

| 信号类型 | 示例 | 置信度 | 入画像条件 |
|---|---|---|---|
| 显式陈述 | "记住我用中文" | 高 | 直接写入 |
| 重复模式 | 连续 N 个会话偏好表格输出 | 中 | 达到出现次数阈值后写入 |
| 单次行为 | 某一次用了表格 | 低 | 不写入（防噪声） |

**合并语义（三个关键判定）**：

1. **冲突处理**：新事实与旧画像矛盾时，稳定层走修订（如主技术栈变更即覆盖），时效层走追加（新旧并存，旧的衰减）
2. **过期策略**：时效层每条带时间戳，超 TTL 在周期蒸馏时降权/清除
3. **防膨胀**：画像设 token 硬上限（实测约 1–2K），超限先压时效层再压稳定层

### 4.6 非功能需求（NFR）

| 编号 | 需求 | 指标/约束 |
|---|---|---|
| NFR-01 | 隐私合规 | 画像数据存储于服务端，须符合数据合规要求；用户可感知数据存在（注入内容用户可见） |
| NFR-02 | 注入性能 | 画像注入不显著增加会话首响应延迟（建议目标 <500ms 增量，非实测） |
| NFR-03 | Token 预算 | 画像 ≤2K token；每轮写入提醒 ≤300 token |
| NFR-04 | 检索性能 | 跨会话检索 P95 <2s（建议目标，非实测） |
| NFR-05 | 一致性 | 画像服务端为唯一权威源；本地缓存可丢弃重建 |
| NFR-06 | 容错 | 本地记忆文件损坏/删除不影响云端层；检索失败可降级为无记忆运行 |

### 4.7 边界与已知限制

1. 画像（云端层）**无直接编辑入口**：用户无法主动改写云端画像内容，只能通过持续行为让系统重新学习覆盖，或用本地 MEMORY.md 显式补充/覆盖偏好——缺少"一键修正画像"能力，体验缺口
2. 静默学习的**知情权**：用户难以知道画像里具体记了什么（只能从 Agent 行为反推）
3. 检索**依赖服务端可用性**，且数据主权在平台侧
4. 本地记忆为明文 Markdown，无加密（依赖机器本身的安全）

## 5. 本地复刻方案（通用 Skill 路径）

### 5.1 可行性矩阵

| 原生能力 | 复刻方式 | 还原度 |
|---|---|---|
| 写入路由规则（FR-08） | SKILL.md 规则文本 | ~100% |
| 每轮写入提醒（FR-07） | Hook 注入（Stop/UserPromptSubmit/PostToolUse） | ~90%（软约束） |
| 分层文件体系 | `~/.agent-memory/` + `{project}/.agent/memory/` | ~100% |
| 云端画像 | 会话结束 LLM 蒸馏 → 本地 profile.md（固定维度） | ~70%（覆盖面限于本地会话） |
| 跨会话检索 | 本地 transcript 全文检索（grep/embedding） | ~70%（取决于 harness 是否落盘会话记录） |
| 只读保护/权威源 | 无服务端，单机无此需求 | N/A |

### 5.2 分期实施

| 阶段 | 内容 | 依赖 |
|---|---|---|
| Phase 1 | memory skill（规则+路由+蒸馏命令）+ AGENTS.md 一行引用 | 无，任何 Agent Skills 兼容 harness |
| Phase 2 | Hook 注入写入提醒；画像 profile.md + 确认制写入 | opencode/OmO hooks、Claude Code hooks |
| Phase 3 | transcript 蒸馏画像 + 本地全文检索 | harness 落盘会话记录（如 `~/.claude/projects/` JSONL） |

### 5.3 与服务端版的关键差异

| 维度 | 服务端版 | 本地版 |
|---|---|---|
| 画像数据源 | 全部历史会话 | 本机落盘的会话 |
| 写入确认 | 静默（不可干预） | 可做确认制（显式自动记，推断需确认）——隐私可控性反超 |
| 跨设备 | 跟随账号 | 跟随机器（需自行同步） |
| 强制力 | 产品级（每轮系统注入） | 脚本级（hook 注入，同为软约束但频率一致） |

## 6. 相关项目与替代方案：TencentDB-Agent-Memory

### 6.1 项目定位

[TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory) 是腾讯云开源（MIT）的**团队级 Agent 记忆中枢**，核心理念"Agents remember. Humans innovate."。它将对话、文档、代码转化为四种可复用记忆资产：

| 资产 | 对应 WorkBuddy 侧概念 |
|---|---|
| Chat Memory（偏好/事实/决策/交互历史） | 云端画像 + 本地 MEMORY.md |
| Skill（带版本/触发/验证的可复用技能） | `~/.workbuddy/skills/` 技能体系 |
| Wiki（文档→结构化页面+链接图） | （WorkBuddy 无对应） |
| CodeGraph（代码符号/调用/影响索引） | （WorkBuddy 无对应） |

### 6.2 分层架构对照

Agent Memory 采用 L0–L3 分层，与 WorkBuddy 体系概念同构：

| Agent Memory | WorkBuddy 对应 | 概念 | 作者权 |
|---|---|---|---|
| L0 Conversation（原始对话） | L1b 跨会话检索（全量索引） | 原始记录 | 均服务端自动 |
| L1 Atom（原子事实） | L1a 云端画像内的蒸馏事实 | 事实提取 | 均自动蒸馏 |
| L2 Scenario（场景知识块） | L3b 项目长期记忆 | 工作上下文 | Agent Memory 自动 / WorkBuddy 显式蒸馏 |
| L3 Core/Persona（长期画像） | L1a 云端画像 | 隐式用户画像 | 均自动 |

> 关键差异：Agent Memory 全层为**自动蒸馏**；WorkBuddy 的 L2 用户级 + L3 工作区为 **Agent/用户显式写入**层，Agent Memory 无直接对应——这是 WorkBuddy 独有的「用户主权记忆」能力，也是其隐私可控性的来源。

检索策略：L2/L3 快速上下文引导，需具体事实时 BM25+向量+RRF 回退到 L1/L0，受字符预算与超时约束（防撑爆上下文）。这与 WorkBuddy"结论常驻 + 原始按需检索"的经济学一致。

### 6.3 与 WorkBuddy 的关系定性

1. **消费关系**：WorkBuddy 被明确列为 Agent Memory 支持的客户端之一（有专门集成指南 `INSTALL.md#using-proxy-with-workbuddy`），即 WorkBuddy 可作为客户端接入 Agent Memory Hub 共享团队记忆——但**这不等于 WorkBuddy 内置的 MEMORY.md 体系由 Agent Memory 提供**。
2. **同源设计**：同为腾讯体系，都采用"对话分层蒸馏到 Persona"架构，L0–L3 与 WorkBuddy 画像/检索/记忆三层高度同构，疑为同源设计思想或 R&D 交叉，但页面未声明实现共享，无法证实。
3. **互补不互斥**：WorkBuddy 本地 MEMORY.md 解决单用户即时记忆；Agent Memory 解决团队跨 Agent 长期治理，两者可叠加。

### 6.4 Build vs Adopt 决策矩阵

第 5 章的本地复刻方案（hook+skill+本地文件，Phase 1-3）本质是"DIY 一个单机版 Agent Memory"。在做之前应先评估是否直接采用：

| 维度 | 自建（本地 skill 路线） | 采用 Agent Memory |
|---|---|---|
| 实现成本 | 高（三期，含 hook/检索/蒸馏全自研） | 低（Proxy 零代码接入） |
| 成熟度 | 从零造 | 已有 L0-L3+多 Agent+治理+版本，v2.0 |
| 数据主权 | 全本地，完全可控 | 服务端存储，团队共享 |
| 隐私可控 | 确认制可做，反超服务端 | 依赖平台合规与可见性 |
| 跨 Agent | 否（每 harness 各写一份） | 是（Claude Code/Codex/WorkBuddy/CodeBuddy 等原生支持） |
| 团队共享 | 否 | private/team/restricted(ACL) 三级 |
| 跨设备 | 跟随机器 | 跟随 Hub |
| 依赖 | 零依赖 | 依赖外部 Hub 可用性 |

**建议**：
- **运维小程序这类多人协作场景** → 优先评估采用 Agent Memory（团队共享+治理是刚需，自建无团队价值）
- **个人多 harness 工作流（opencode 主场）** → Phase 1 本地 skill 先跑通（零依赖、数据本地），若检索/画像需求加重再接入 Agent Memory
- **混合路线**（推荐）：本地 skill 处理即时记忆 + Agent Memory 处理团队/长期/跨 Agent 记忆，二者职责互补
