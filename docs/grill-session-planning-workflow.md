# Grill Session: 开发任务规划流程决议

> 日期：2026-06-25
> 主题：讨论关于开发任务中规划流程相关问题，提升思考完整性，减少思维盲区
> 方法：grill-with-docs，逐一走完决策树每个分支

## 决议摘要

本次对话对开发任务规划流程进行了系统性拷问，从需求入口到实施落地，逐一解决了以下关键问题，最终形成了基于 pocock-agents 设计模式的新流程框架。

---

## 决策 1：需求入口

**问题**：需求的入口是否需要区分来源？

**决议**：不需要区分来源。需求大多通过 grill-with-docs 对话中产生（包括改进想法），不区分 bug/feature/想法等来源。

**理由**：grill-with-docs 兼具"需求发现"和"需求对齐"双重职责——用户带着模糊想法进来，通过拷问逐步具象化并达成对齐。

---

## 决策 2：grill-with-docs 的双重职责

**问题**：grill-with-docs 的作用是"对齐已有需求"还是"发现需求"？

**决议**：grill-with-docs 兼具两个职责——"需求发现"和"需求对齐"是同一个对话过程的两个阶段，不需要拆成两个步骤。

**关键洞察**：用户一开始可能有模糊想法（"我要开发一个 XXX"），grill-with-docs 根据需求边界、实际限制等拷问用户，迫使做抉择，把模糊需求具象化，在此过程中逐步达成人和 LLM 需求对齐。

---

## 决策 3：grill 退出条件

**问题**：grill-with-docs 结束的判定条件是什么？

**决议**：四项检查全绿 + 用户确认退出。

四项检查：
1. **术语完整性**：本次对话引入的每个核心概念，是否都在 CONTEXT.md 中有明确定义？
2. **决策点闭合**：每个已打开的决策分支，是否都有明确结论？
3. **边界明确性**：需求范围是否清晰——哪些"做"、哪些"不做"、哪些"以后再说"？
4. **实施可行性**：当前的需求描述是否足够让一个实施 agent 开始工作？

**退出机制**：LLM 在每次决策点关闭后做四项检查，如果全绿建议退出，任一红灯继续拷问该方向。用户最终确认退出。

**研究依据**：grill-with-docs skill 本身没有退出条件定义，只说"until we reach a shared understanding"，"shared understanding"是主观的。退出条件需要流程层补充。

---

## 决策 4：流程中规则 vs 建议

**问题**：流程中哪些是"必须遵守的规则"，哪些是"LLM 给建议、用户决定"？

**决议**：

| 环节 | 性质 | 谁决定 |
|---|---|---|
| grill-with-docs 不可跳过（有决策点时） | 规则 | 强制 |
| 复杂度判定 | 建议 | 用户 |
| 是否生成 PRD | 建议 | 用户（主动调用 /to-prd） |
| 实施方式选择 | 建议 | 用户 |
| 退出 grill | 建议+确认 | LLM 建议，用户确认 |
| 复杂度升级/回退 | 自由 | 用户自行 |

**唯一硬性规则**：有决策点时 grill-with-docs 不可跳过。其余均由用户决定，LLM 提供建议和风险提示。

---

## 决策 5：PRD 层的必要性

**问题**：PRD（需求文档化）是否必须？

**决议**：需要，除非"简单修改且毫无争议"（≤1 决策点且决策点无关紧要）。

**理由**：grill 产出的对齐结果存在对话中，对话是临时的。如果实施跨会话或交给不同 agent，没有文档化的需求就是信息丢失。PRD 的价值不是仪式感，是把对齐结果持久化。

**豁免条件**：≤1 决策点且决策点无关紧要——即决策点存在但不影响实施方向。

---

## 决策 6：逐级收紧原则

**问题**：PRD 是逐级收紧的必要前提还是原则的一种实现方式？

**决议**：逐级收紧是原则而非强制 PRD。PRD 是实现该原则的常用方式但不是唯一方式——grill 的对话结论也可以作为约束源。

**理由**：如果用户判断中等需求但选择不写 PRD，grill 产出的对齐结论（对话中 + CONTEXT.md + ADR）仍然提供约束。强制"没有 PRD 就不能做 issues"会增加仪式感。

---

## 决策 7：实施中的越界处理

**问题**：实施 agent 发现更优方案但超出 acceptance criteria 范围时怎么办？

**决议**：暂停，向用户建议修改 acceptance criteria，用户批准后调整。

**原则**：越界不是禁止，而是需要回到约束源（用户）重新对齐。影响其他切片或改变对齐时的决策 → 停下来问人。

---

## 决策 8：复杂度升级/回退

**问题**：用户判断复杂度错误时怎么办？

**决议**：不需要形式化的升级机制。用户判断错了，重新对齐需求即可。

**理由**：流程中大部分是"LLM 建议、用户决定"。如果用户选错了，自然会发现并回来。

---

## 决策 9：验证回路

**问题**：每个 issue 完成后，人类检查点检查什么？

**决议**：本次对话未对验证回路的具体操作做出最终决议。验证发生在多个层级——issue 完成检查 acceptance criteria、组完成检查协调性、全部完成做需求对齐回查。具体操作待后续实践明确。

**关联发现**：这是一个方法论嫁接的典型空白地带——不同方法论有不同的验证机制，嫁接时需要统一定义。

---

## 决策 10：偏移的根因分析

**问题**：Prometheus→Atlas 会偏移，根因是什么？

**决议**：偏移的根因是"执行过程缺约束守卫"。

四种偏移类型：
1. 需求理解偏移——agent 读 issue/plan 理解错
2. 决策越权——agent 自行做超出范围的决策
3. 实施质量偏移——代码结构差、过度设计
4. 范围蔓延——做了没要求的功能

两套流程（Matt Pocock 和 omo）都缺同一层东西：实施过程中的约束守卫。

---

## 决策 11：选择框架的修正

**问题**：选择实施方案的关键维度是什么？

**决议**：最初用"复杂度"作为选择维度，后修正为"偏移代价"。

**修正理由**："复杂"不一定等于"偏移代价高"。比如复杂 CRUD 生成器偏移代价低，而中等复杂度核心算法偏移代价极高。偏移代价才是比复杂度更准确的维度。

**但最终方案不再依赖单一维度选择**——采用 pocock-agents 模式后，选择逻辑变为：独立+简单→todo，有依赖/复杂→orchestrator+worker。

---

## 决策 12：SuperPowers 的定位

**问题**：SuperPowers write-plan→subagent 在流程中的位置？

**决议**：SuperPowers 的定位是"执行放大器"，不是"规划助手"。它放大计划的质量，也放大计划的缺陷。只适合"人类已想清楚每一步"的窄场景。

**研究依据**：
- brainstorming 的"草率"不是 skill 设计问题，是 LLM 遵从度问题
- "精确偏移"被强烈证实——所有审查门通过但产出和决策矛盾
- 框架明确假设用户是有经验的工程师
- 框架反复尝试修复计划质量问题但都失败了（子代理审查被移除、对抗性审查被撤回）

---

## 决策 13：Prometheus→Atlas 的定位

**问题**：Prometheus→Atlas 在新流程中的位置？

**决议**：Prometheus→Atlas 作为备选方案。大多数时候使用 TDD worker（Sisyphus-Junior），当某个 issue 特别复杂时可以单独对那个 issue 用 Prometheus→Atlas。

**理由**：
- Prometheus 生成的大计划审查难、版本混乱
- to-issues 垂直切片天然降低复杂度，比大计划更具可行性
- 但某些特别复杂的 issue 可能需要 Prometheus 的面试+规划能力

---

## 决策 14：核心流程——基于 pocock-agents 模式

**问题**：最终落地方案是什么？

**决议**：基于 pocock-agents 的设计模式，自建 orchestrator/worker 体系。

完整流程：

```
grill-with-docs（需求发现+对齐）
    ↓ 退出：四项检查全绿 + 用户确认
to-prd（需求文档化，用户主动调用）
    ↓ ≤1 决策点且无关紧要可豁免
to-issues（垂直切片）
    ↓ 用户确认粒度
按依赖关系分组：
    ├── 独立+简单 → todo 直接做
    └── 有依赖/复杂 → 依赖连通子图
        ├── 组内：orchestrator + TDD worker
        ├── 组间：依赖组 B→C，C 等 B 完成后启动
        └── 复杂 issue 备选：Prometheus→Atlas
    ↓
每个 issue/组 完成后 → 人类检查点
    ↓
验证回路（全量测试 → 需求对齐回查 → commit）
```

---

## 决策 15：依赖分组规则

**问题**：to-issues 产出的 issue 如何分组执行？

**决议**：

分组规则：
1. **完全独立 + 简单** → todo 直接做
2. **有依赖关系的一组 issue** → orchestrator + TDD worker 执行
3. **独立但复杂** → orchestrator + TDD worker 执行

组间依赖推导：组 X 依赖组 Y ⟺ ∃(x∈X, y∈Y) 使得 x blocked-by y

组间上下文传递：下一组 Prometheus 生成 plan 时重新扫描代码库获取上一组的实际产出（代码是事实，不需要人工交接文档）。

---

## 决策 16：Worker 角色设定

**问题**：Worker（执行 agent）由谁承担？

**决议**：沿用 pocock-agents 的设定——Sisyphus-Junior 作为 TDD worker，当前对话 agent 作为 orchestrator。

Worker 约束（基于 pocock-agents 设计模式）：
- Skill 白名单：只加载 `tdd`、`diagnose` 等执行类 skill，不加载 `to-prd`、`to-issues`
- 权限控制：禁止 `git push --force`、`git reset --hard`、`git clean`
- 自治但不自主：自己做决策但限于 issue 边界内
- One issue only：不跨 issue，发现相关问题记入摘要交 orchestrator

---

## 决策 17：issue → Atlas 的桥接问题

**问题**：Atlas 能否直接消费 to-issues 的产出？

**研究结论**：不能。Atlas 硬编码读取 `.omo/plans/*.md`，无法对接 issue tracker。issue 和 Atlas plan 之间有结构性鸿沟——issue 缺少 Recommended Agent Profile、QA scenarios、Final Verification Wave 等元数据。

**决议**：不桥接。用 TDD worker 直接消费 issue，而不是让 Atlas 消费。避免了转换层的复杂度。

---

## 决策 18：方法论嫁接的可行性

**问题**：方法论嫁接是否可行？

**研究发现**：方法论嫁接不是一个人困惑，是整个社区的共同探索。已有多个具体项目：

| 项目 | 嫁接方式 | 状态 |
|---|---|---|
| pocock-agents | Matt Pocock skills + orchestrator/worker agent | 14 stars，个人项目，有已知 bug |
| oh-my-superpowers | SuperPowers 流程 + omo agent 角色映射 | 6 stars，桥接映射表 |
| Slice Driven Development | 垂直切片 + Coordinator/Executor 模式 | 1 star，独立 skill |
| CORE Workflow | 计划/执行分离会话 | 独立模式 |
| shipsmooth | 风险优先排序 + 垂直切片 | 独立 skill |
| open-artisan | 状态机强制分阶段 + 隔离审查 | 独立 agent |

**结论**：方法论嫁接可行，但需要注意嫁接点的验证空白。pocock-agents 模式最符合当前需求。

---

## 决策 19：pocock-agents 项目评价

**问题**：pocock-agents 项目的成熟度如何？

**客观评价**：
- 14 stars，1 个 fork，1 个 issue（报 bug：task-observer 引用不存在）
- 只有 2 个 commit，无测试、无 CI
- 作者自述"不是码农"，项目本质是两个 markdown 文件（系统提示词）
- 有已知 bug，且维护策略是"让 LLM 自己更新就行"

**决议**：不直接使用 pocock-agents 项目，而是**提取其设计模式**——角色分离、依赖波编排、skill 白名单、worktree 隔离、入口分流。自建优化后的 agent 配置。

## 附录：术语表

| 术语 | 定义 | 避免使用 |
|---|---|---|
| **需求发现** | grill-with-docs 中从模糊想法到具象需求的过程 | 需求创造、需求生成 |
| **需求对齐** | grill-with-docs 中人机达成共享理解的过程 | 需求确认、需求审批 |
| **退出条件** | grill-with-docs 结束的判定标准：四项检查全绿 + 用户确认 | 完成条件、终止条件 |
| **偏移代价** | 实施偏移后修正的成本——决定选择何种约束强度 | 偏移风险、偏移概率 |
| **精确偏移** | 所有审查门通过但产出和原始决策矛盾——审查验证的是代码符合计划，不是计划符合现实 | 质量偏移、合规偏移 |
| **依赖连通子图** | to-issues 产出中，由 blocked-by 关系确定的连通 issue 组，作为执行分组依据 | 依赖组、任务组 |
| **依赖波** | 按依赖关系分组的并行执行批次：波内并行、波间串行 | 执行波、并行波 |
| **约束守卫** | 实施过程中防止偏移的机制——TDD、PR 审查、人类检查点等 | 约束机制、防偏移 |
| **垂直切片** | 切穿所有层的窄但完整的端到端路径，可独立验证 | 功能模块、开发任务 |
| **依赖组间依赖** | 组 X 依赖组 Y ⟺ ∃(x∈X, y∈Y) 使得 x blocked-by y | 组间阻塞、跨组依赖 |
| **角色分离** | orchestrator 负责规划调度不写代码，worker 负责实施不规划 | 代理分工、任务分配 |
