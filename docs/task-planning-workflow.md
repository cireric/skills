# Task Planning Workflow

按任务复杂度选择规划方式，避免过度仪式或欠规划。

核心理念：**需求对齐是 agentic coding 最关键的阶段**。跳过对齐直接实施 = agent 用自己的理解代替你的意图，产出偏离需求。

## 决策树

```
需求/想法
    ↓
是否有决策点或歧义？
    ├── 否 → todo 直接做
    └── 是 → grill-with-docs（需求发现+对齐）
                ↓ 退出：四项检查全绿 + 用户确认
            to-prd（需求文档化，用户主动调用）
                ↓ ≤1 决策点且无关紧要可豁免
            复杂度判断（用户判断，LLM 建议）
                ↓
            ├── 简单 → todo 直接做
            └── 中高复杂 → to-issues（垂直切片）
                                ↓ 用户确认粒度
                            按依赖关系分组：
                            ├── 独立+简单 → todo
                            └── 有依赖/复杂 → 依赖连通子图
                                ├── 组内：orchestrator + TDD worker
                                ├── 组间：B→C 依赖，C 等 B 完成后启动
                                └── 复杂 issue 备选：Prometheus→Atlas
                                ↓
                            每个 issue/组 完成后 → 人类检查点
                                ↓
                            验证回路（全量测试 → 需求对齐回查 → commit）
```

## 复杂度评估

不用"步数"判断——"步"的定义因人而异。用以下两个信号：

| 信号 | 简单 | 中等 | 复杂 |
|------|------|------|------|
| **涉及模块数** | 1 | 1-2 | 3+ |
| **决策点数量** | 0-1 | 2-3 | 4+ |
| **是否需要跨文件协调** | 否 | 有限 | 是 |

- **模块** = 一个有独立接口的代码单元（一个 Python 文件、一个 React 组件、一个 API endpoint）
- **决策点** = 需要人工确认的选择（接口设计、数据结构、依赖取舍、架构方案）

复杂度由用户判断，LLM 提供建议和风险提示。用户判断错误时重新对齐需求即可，不需要形式化的升级机制。

### 典型例子

| 任务 | 模块 | 决策点 | 复杂度 | 流程 |
|------|------|--------|--------|------|
| 修 typo | 1 | 0 | 简单 | todo 直接做 |
| 加一个 config 字段 | 1 | 1 | 简单 | todo 直接做 |
| reporter.py 加 test conditions 表格 | 1 | 2 | 中等 | grill → to-prd → to-issues → worker |
| 新增 i18n 标签系统 | 2 | 3 | 中等 | grill → to-prd → to-issues → worker |
| 重构整个 gateway 检查体系 | 5+ | 8+ | 复杂 | grill → to-prd → to-issues → 依赖分组 → worker |

## 阶段 1：需求发现与对齐 — grill-with-docs

这是整个流程中最重要的一步。不可跳过。

### 双重职责

grill-with-docs 兼具两个职责：

1. **需求发现**：用户带着模糊想法进来，grill 拷问迫使做抉择，把模糊需求具象化
2. **需求对齐**：逐一走完决策树每个分支，agent 提供推荐答案，用户确认或纠正

这两个职责是同一个对话过程的两个阶段，不需要拆成两个步骤。

### 触发条件

- 任务有 ≥1 个决策点或存在歧义
- 不触发：改 typo、加字段、修 lint error 等无需对齐决策的任务

### grill-with-docs 做什么

1. **拷问需求**：逐一走完决策树的每个分支，agent 提供推荐答案，用户确认或纠正
2. **术语对齐**：遇到模糊或冲突的术语，当场决议并更新 CONTEXT.md
3. **架构决策**：遇到不可逆决策，记录 ADR
4. **代码交叉验证**：用户说"X 是这样工作的"，agent 检查代码是否一致，不一致则暴露

### 退出条件

grill-with-docs skill 本身没有定义退出条件。流程层补充以下退出机制：

LLM 在每次决策点关闭后做四项检查：

1. **术语完整性**：本次对话引入的每个核心概念，是否都在 CONTEXT.md 中有明确定义？有没有"说了但没定义"的词？
2. **决策点闭合**：每个已打开的决策分支，是否都有明确结论（选了 A 还是 B）？有没有"讨论了但没拍板"的点？
3. **边界明确性**：需求范围是否清晰——哪些"做"、哪些"不做"、哪些"以后再说"？有没有"可能要做也可能不做"的模糊地带？
4. **实施可行性**：当前的需求描述是否足够让一个实施 agent 开始工作？如果交给另一个 agent，它会不会卡住？

四项全绿 → LLM 建议退出。任一红灯 → 继续拷问该方向。用户最终确认退出。

### 为什么不可跳过

- 术语不对齐 → 后续实施用词不一致，agent 产生歧义
- 决策不对齐 → agent 用自己的理解代替你的意图，产出偏离需求
- grill 的价值不只是"问清楚"——它还建立术语基础设施（CONTEXT.md）和决策记录（ADR），后续所有实施都依赖它们

### 产出

- 对齐后的需求理解（在对话中）
- 更新的 CONTEXT.md（术语决议）
- 更新的 ADR（架构决策，按需）

## 阶段 2：需求文档化 — to-prd

### 必要性

grill 产出的对齐结果存在对话中，对话是临时的。如果实施跨会话或交给不同 agent，没有文档化的需求就是信息丢失。PRD 的价值不是仪式感，是把对齐结果持久化。

### 调用方式

用户主动调用 `/to-prd`，LLM 做好辅助给建议即可。

### 豁免条件

≤1 决策点且决策点无关紧要——即决策点存在但不影响实施方向。

### 逐级收紧原则

逐级收紧是**原则**而非强制 PRD。PRD 是实现该原则的常用方式但不是唯一方式——grill 的对话结论也可以作为约束源。如果用户判断中等需求但选择不写 PRD，grill 产出的对齐结论（对话中 + CONTEXT.md + ADR）仍然提供约束。

## 阶段 3：垂直切片 — to-issues

### 切片粒度

to-issues 的垂直切片规则：

| 规则 | 含义 |
|---|---|
| 窄但完整 | 每个切片切穿所有层（schema→API→UI→test），不是按层拆 |
| 可独立验证 | 完成后可以 demo 或测试，不等后续切片 |
| 偏细不偏粗 | 宁可多个薄切片，不要少数厚切片 |
| 太细信号 | agent 启动时间 > 实际实现时间，应合并 |
| 太粗信号 | 标题是层名（"Backend resolver"）而非行为（"用户可以提交评论"） |

粒度判断靠人类，skill 只提供方向性指导。

### 产出

- issue 列表（标题 + acceptance criteria + blocked-by + HITL/AFK 标记）

## 阶段 4：实施

### 分组规则

按依赖关系对 issue 分组，决定执行方式：

| issue 特征 | 执行方式 | 理由 |
|---|---|---|
| 完全独立 + 简单 | todo 直接做 | 不需要编排 |
| 有依赖关系的一组 issue | orchestrator + TDD worker | 需要编排 |
| 独立但复杂 | orchestrator + TDD worker | 需要约束 |

分组依据是**依赖连通子图**——由 blocked-by 关系确定的连通 issue 组。

### 组间依赖

组 X 依赖组 Y ⟺ ∃(x∈X, y∈Y) 使得 x blocked-by y

执行顺序：有依赖关系的组串行，无依赖的组可并行。下一组启动前扫描代码库获取上一组的实际产出。

### orchestrator + TDD worker 模式

基于 pocock-agents 设计模式（角色分离）：

**Orchestrator（当前对话 agent）职责**：
- 规划调度——什么时候加载哪个 skill，什么时候派发 worker
- 管理 git worktree 生命周期
- 协调依赖波——波内并行、波间串行
- 不写代码

**Worker（Sisyphus-Junior）职责**：
- 拿一个 issue + worktree，用 TDD 实施并开 PR
- 自治但不自主——自己做决策但限于 issue 边界内
- One issue only——不跨 issue

**Worker 约束**：
- Skill 白名单：只加载 `tdd`、`diagnose`、`zoom-out` 等执行类 skill，不加载 `to-prd`、`to-issues`
- 权限控制：禁止 `git push --force`、`git reset --hard`、`git clean`
- 遵守 CONTEXT.md 术语和 ADR 决策

**偏移防护（5 层）**：

| 层 | 机制 | 防护什么 |
|---|---|---|
| 1 | 垂直切片边界 | 每个 issue 范围窄，偏移空间小 |
| 2 | TDD 红绿重构 | 代码必须通过行为测试，不能写推测性功能 |
| 3 | Worktree 隔离 | worker 之间不互相干扰，失败可独立回退 |
| 4 | PR 审查 | 人类最终检查点，代码合并前必须审查 |
| 5 | diagnose skill | bug 反馈时结构化排查，不是乱改 |

### Prometheus→Atlas 备选

当某个 issue 特别复杂，需要面试式规划+专业 agent 编排时，可以单独对该 issue 使用 Prometheus→Atlas。但大多数时候使用 TDD worker。

### 实施中的越界处理

实施 agent 发现更优方案但超出 acceptance criteria 范围时：
- 暂停，向用户建议修改 acceptance criteria，用户批准后调整
- 越界不是禁止，而是需要回到约束源（用户）重新对齐
- 影响其他切片或改变对齐时的决策 → 停下来问人

### 实施中按需使用的 skill

| Skill | 触发时机 | 用途 |
|-------|----------|------|
| `/tdd` | 实现新功能或修 bug 时 | 红绿重构循环，一次一个垂直切片 |
| `/diagnose` | 遇到 bug 或测试失败时 | 6 阶段排查：建反馈循环→复现→假设→仪器→修复→清理 |
| `/improve-codebase-architecture` | 发现模块过浅或耦合过紧时 | 深化模块，提高可测试性和 AI 可导航性 |
| `/zoom-out` | 不熟悉某段代码的全局角色时 | 跳出细节，看模块在系统中的位置 |
| `/prototype` | 架构决策前需要验证方案时 | 抛弃式原型，验证后删除或吸收 |

## 阶段 5：验证回路

实现完成后的验证流程：

1. **全量测试**：`pytest` 全绿（零失败，pre-existing 失败单独标注）
2. **需求对齐回查**：回读 grill 阶段的决策，确认：
   - 每条决策在代码中有对应实现
   - 代码中的实际实现没有超出决策范围（scope creep）
3. **对齐失败时**：更新决策记录使其与实际一致（以代码为准），不回退代码去迎合过时决策

### 谁来判定

| 验证项 | 判定者 | 通过后 | 失败时 |
|--------|--------|--------|--------|
| 全量测试 | 自动 | 进入下一步 | 修复代码，重跑 |
| 需求对齐 | agent + 人工 | commit | 修复代码或更新决策记录 |

全部通过 → commit（需人工确认）。不自动 commit。

## 背景决策记录

### 规则：grill-with-docs 不可跳过

- **问题**：跳过对齐直接实施，术语不对齐导致 agent 各说各话，决策不对齐导致产出偏离需求
- **解法**：grill-with-docs 在对齐决策的同时更新 CONTEXT.md + ADR，建立术语基础设施
- **结论**：grill 兼具需求发现和需求对齐双重职责，价值不只是"问清楚"——它还建立术语基础设施，后续所有实施都依赖它

### 规则：复杂任务拆分垂直切片

- **问题**：大功能整体实施，agent 自由度过大，容易"创造性发挥"偏离需求；Prometheus 生成的大计划审查难、版本混乱
- **解法**：拆成垂直切片，每个切片切穿所有层，逐片验证。to-issues 天然降低复杂度
- **结论**：小切片比大计划更具可行性

### 规则：按依赖分组执行

- **问题**：issue 列表如何编排执行——简单 todo、依赖分组、Prometheus→Atlas？
- **解法**：按依赖连通子图分组，独立+简单→todo，有依赖/复杂→orchestrator+TDD worker
- **结论**：分组依据是 blocked-by 关系，组间依赖显式化

### 规则：角色分离（orchestrator/worker）

- **问题**：to-issues 之后存在实施空白地带——Matt Pocock 方法论未定义如何实施
- **解法**：基于 pocock-agents 设计模式，orchestrator 负责规划调度不写代码，worker 负责实施不规划
- **结论**：角色分离填补空白，而不是用额外的计划层

### 规则：同文件变更串行执行

- **问题**：两个 agent 并行改同一文件，合并时丢失改动或测试失败
- **解法**：同文件的变更串行；不同文件的变更可并行（worktree 隔离）
- **结论**：并行安全靠 worktree 隔离保证

### 规则：逐级收紧是原则而非强制 PRD

- **问题**：跳过 PRD 直接实施时，约束链怎么生效？
- **解法**：grill 的对话结论也可以作为约束源，不强制 PRD
- **结论**：PRD 是实现逐级收紧的常用方式但不是唯一方式

### 规则：Prometheus→Atlas 作为备选而非主力

- **问题**：Prometheus→Atlas 执行偏移，大计划审查困难
- **解法**：大多数时候使用 TDD worker，Prometheus→Atlas 仅用于特别复杂的 issue
- **结论**：避免两系统组合的复杂度叠加，保留备选灵活性

### 规则：SuperPowers 仅用于"人类已想清楚"的窄场景

- **问题**：SuperPowers 规划草率但执行精确——"精确偏移"风险
- **解法**：SuperPowers 定位为"执行放大器"，只用于人类已想清楚每一步的场景
- **结论**：大多数时候不需要 SuperPowers，TDD worker 的偏移防护更全面

详细的决策推理过程见 `docs/grill-session-planning-workflow.md`。
